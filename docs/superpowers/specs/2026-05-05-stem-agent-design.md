# Stem Agent — Design Spec
**Date:** 2026-05-05  
**Domain:** Deep Research (demo)  
**Stack:** Python + OpenAI API  
**Approach:** Iterative Evolution Loop (Approach B)

---

## 1. Problem Statement

Build a stem agent — a minimal AI agent that takes a class of problems as input and self-specializes into a domain-specific agent through its own process. Like a stem cell reading environmental signals, the agent must figure out what architecture, tools, and skills it needs, rebuild itself, and know when to stop evolving.

**Key questions the design must answer:**
- How does it learn how a domain is approached?
- How does it decide what to become?
- How does it rebuild itself without breaking?
- How does it know when it is good enough?

## 3. Phase 1 — Discovery

The stem agent learns how experts in the given domain work using two simultaneous signals.

### LLM Introspection
Queries the LLM with structured prompts:
- "How do expert deep researchers approach problems step by step?"
- "What tools and capabilities does a high-quality research agent need?"
- "What does an excellent research output look like? What are the failure modes?"

### Web Research
Executes targeted searches:
- `"deep research AI agent architecture"`
- `"best practices AI research agents"`
- `"deep research agent evaluation benchmarks"`

Scrapes and extracts structured insights from top results.

### Output — DomainProfile

```python
{
  "domain": "Deep Research",
  "workflow": [
    "query decomposition",
    "multi-source search",
    "cross-referencing",
    "synthesis",
    "citation"
  ],
  "required_tools": [
    "web_search",
    "url_reader",
    "summarizer",
    "citation_extractor",
    "fact_checker"
  ],
  "quality_criteria": [
    "factual accuracy",
    "source coverage",
    "synthesis quality",
    "citation quality"
  ],
  "benchmark_tasks": ["<5 research questions generated by LLM during discovery, validated for answerability and saved to benchmarks/deep_research_tasks.json with ground-truth answers>"]
}
```

**Caching:** DomainProfile is saved to `cache/{domain}.json` after first run. Subsequent runs skip discovery unless `--force-rediscover` is passed.

## 4. Phase 2 — Specialization

### Step 1: Prompt Rewriting
The base generic system prompt is rewritten to embed the domain workflow, quality criteria, and specialist persona.

```
BEFORE: "You are a helpful AI assistant."

AFTER:  "You are a Deep Research specialist. For every query:
         1. Decompose into focused sub-questions
         2. Search multiple independent sources per sub-question
         3. Cross-reference facts across sources before accepting them
         4. Synthesize findings into a coherent narrative
         5. Support every claim with an explicit citation
         Quality bar: factual accuracy, broad source coverage,
         coherent synthesis, properly cited claims."
```

### Step 2: Tool Specification → Generation → Registration

For each tool name in `required_tools`, the process is three steps:

**Step 2a — Spec generation (name → spec):**
Before generating code, the LLM produces a structured tool spec:
```python
{
  "name": "fact_checker",
  "description": "Verifies a factual claim against a web source",
  "parameters": {
    "claim": {"type": "string", "description": "The claim to verify"},
    "source_url": {"type": "string", "description": "URL to check against"}
  },
  "returns": {"type": "object", "fields": ["verified", "confidence", "evidence"]}
}
```

**Step 2b — Code generation (spec → Python):**
The tool spec drives code generation. If the tool already exists in `tools/` → skip generation, go to 2c.
If missing → generate Python implementation via LLM using the spec, then apply safety gates:

```
Generated code
     │
     ├──▶ Syntax check     — ast.parse()
     ├──▶ Static analysis  — block dangerous imports (os.system, subprocess, eval)
     ├──▶ Dry run          — execute with mock input, catch exceptions
     │
     ├── PASS → save to tools/generated/{name}.py
     └── FAIL → log failure, skip tool, flag for next iteration
               (max 2 retries with refined spec before skipping)
```

**Step 2c — OpenAI schema registration:**
Each tool's spec is converted to an OpenAI function-calling JSON schema and registered in the agent's active tool list:
```python
{
  "type": "function",
  "function": {
    "name": "fact_checker",
    "description": "Verifies a factual claim against a web source",
    "parameters": {
      "type": "object",
      "properties": {
        "claim": {"type": "string"},
        "source_url": {"type": "string"}
      },
      "required": ["claim", "source_url"]
    }
  }
}
```

**Versioned snapshot** is taken after every successful specialization cycle. This is the rollback point.

## 5. Phase 3 — Evaluation

### Agent Execution Model
The specialized agent uses a **ReAct-style loop** (Reason → Act → Observe → Repeat) powered by OpenAI's `chat.completions` API with function calling:
```
User query (benchmark task)
     │
     ├──▶ GPT-4o reasons about next step
     ├──▶ Calls a registered tool (function call)
     ├──▶ Observes tool result (injected as tool message)
     └──▶ Repeats until agent emits a final answer (no tool call)
```
Max 10 tool calls per task to prevent infinite loops. If exceeded, the current partial answer is used for scoring.

### Benchmark
5 fixed Deep Research tasks drawn from the **FRAMES benchmark** (a public factual multi-hop research QA dataset) — not LLM-generated — to avoid circular ground truth. Tasks and reference answers are stored in `benchmarks/deep_research_tasks.json`.

### Scoring Rubric

| Criterion | Measurement Method | Normalization | Weight |
|---|---|---|---|
| Factual Accuracy | Single batched GPT-4o call scores all 5 outputs vs. reference answer, returns 0–10 JSON scores | Already 0–10 | 35% |
| Source Coverage | Count of unique domains cited in output | `min(count / 5, 1) × 10` | 25% |
| Synthesis Quality | Same batched GPT-4o judge call scores coherence and depth, returns 0–10 | Already 0–10 | 25% |
| Citation Quality | % of sentences in output that contain an inline citation | `ratio × 10` | 15% |

**Composite Score** = `(accuracy×0.35 + coverage×0.25 + synthesis×0.25 + citation×0.15)` → 0–100 scale

**Tiered model rule:** Use `gpt-4o-mini` as the judge for all iterations except the final one (when stopping criteria are met). Use `gpt-4o` for the final evaluation only. This cuts judge costs by ~80%.

**Partial evaluation handling:** If a benchmark task fails (API timeout, agent crash), that task scores 0 on all criteria. The run continues with remaining tasks.

### Before/After Comparison (target output)

```
Iteration │ Model Used    │ Tools │ Composite Score
──────────┼───────────────┼───────┼────────────────
0 (base)  │ gpt-4o        │ 1     │ ~30
1         │ gpt-4o        │ 3     │ ~52
2         │ gpt-4o        │ 5     │ ~68
3         │ gpt-4o        │ 5     │ ~74  ← threshold met
```

Iteration 0 is the truly unspecialized baseline: generic prompt, only `web_search` tool, no discovery run.

### Stopping Criteria
The evolution loop halts when any of the following is true:
1. Composite score ≥ **75** (threshold θ)
2. Score improvement < **3 points** over the last 2 consecutive iterations
3. Maximum **5 iterations** reached

### Rollback Trigger
If iteration N scores lower than iteration N-1, `SafeguardManager` restores the previous versioned state and disables further code generation for the failing tool in that run.

## 6. Phase 4 — Diagnose & Refine

When score < θ and stopping criteria not met:

```
Per-criterion breakdown
     │
     ├──▶ Identify lowest-scoring criterion
     ├──▶ LLM diagnoses root cause:
     │     "Factual Accuracy low → missing fact_checker tool
     │      and no cross-referencing step in prompt"
     ├──▶ Targeted patch:
     │     ├── Add missing workflow step to system prompt
     │     └── Retry generating failed tool with refined spec
     └──▶ Re-run evaluation → loop continues
```

Diagnosis is targeted — only the underperforming criterion is addressed. Full re-specialization is not triggered unless the DomainProfile itself is deemed incomplete.

## 7. Versioned State Definition

A `VersionedState` object contains everything needed to fully restore an agent to a previous iteration:

```python
{
  "version": 2,
  "system_prompt": "You are a Deep Research specialist...",
  "active_tools": ["web_search", "url_reader", "summarizer"],
  "tool_schemas": [...],          # OpenAI JSON schemas for active tools
  "tool_source_files": {          # Map of tool name → generated source code
    "url_reader": "def url_reader(url): ...",
    "summarizer": "def summarizer(text): ..."
  },
  "composite_score": 68.2,
  "timestamp": "2026-05-05T14:32:00Z"
}
```

States are saved to `results/versions/v{N}.json` after each evaluation. Rollback restores the state dict, re-registers tools from source files, and continues from the restored point.

## 9. Final Artifact

When the evolution loop completes, the stem agent saves the final specialized agent as a self-contained runnable artifact:

```
results/
└── final_agent/
    ├── agent_config.json       # system_prompt, active tool list, scores
    ├── tools/                  # copies of all active tool source files
    └── run.py                  # standalone script to run the specialized agent
```

`run.py` loads `agent_config.json`, registers the tools, and accepts a query from `stdin` — making the specialized agent independently runnable without the stem agent harness.

## 10. Token Cost Mitigations

| Strategy | Implementation |
|---|---|
| Tiered model usage | `gpt-4o-mini` for tool gen, code validation, intermediate scoring; `gpt-4o` for final eval and judge |
| Small benchmark set | Fixed at 5 tasks |
| Cache discovery | DomainProfile saved to disk after first run |
| Cache web search | URL content cached per session |
| Batch scoring | All 5 task outputs scored in one judge call |
| Hard iteration cap | Max 5 iterations |

**Estimated cost per full run:** < $1.00 USD

## 12. Full System Flow

```
main.py: stem_agent.run("Deep Research")
    │
    1. Discovery → DomainProfile (cached after first run)
    2. Specialize → new system prompt + generated tools (versioned snapshot)
    3. Evaluate → composite score on 5 benchmark tasks
    4. Score ≥ 75?  → DONE, return final specialized agent
       Score < 75?  → Diagnose → targeted patch → goto 2
       Score drop?  → Rollback to previous snapshot → halt code gen → goto 3
       Max iters?   → Return best-scoring version
```
